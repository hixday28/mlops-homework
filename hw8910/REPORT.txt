3. Граф задач и кеш

prepare-input → get-existing-artifact → check-complete-evaluation → publish-accepted
При отказе последняя задача не запускается. Prefect использует локальный API :4208, сохранённый LocalFileSystem block и persist_result; в результаты передаются URI, IDs, SHA и числа, не веса/тензоры.
Подготовка действительно проверяет JSONL, уникальные ID, choices/expected, применяет исходный chat template и считает длины настоящим токенизатором. Ключ — SHA256 canonical JSON {data_sha256, config}. В config точная tokenizer revision, tokenizer hash, template hash, max_length, версия обработки и автоматически вычисляемый implementation_sha256; также настройки рендеринга. Путь/mtime и порядок ключей не участвуют.
Данные и результат подготовки сохраняются на диске. Результат — небольшой JSON в .prefect/validated/prepared, Prefect state/result — в .prefect/results и SQLite локального сервера. Первый опыт явно использует --refresh-preparation, чтобы повторная демонстрация не зависела от старых запусков; восстановление этот флаг не использует.
Кеширование подготовки отделено от publication id: попытка имеет новый UUID/flow_run_id, одинаковые входы имеют одинаковый cache_key, одинаковое решение выпуска имеет одинаковый release_id.

5. Атомарность, WAL и отрицательные случаи

release.publish сначала проверяет полный bound report и файлы, пишет tempfile рядом с accepted, flush/fsync и os.replace. До commit point старая версия неизменна, при ошибке замены tmp удаляется. Отдельный publication-intent хранит manifest/decision до изменения указателя. После commit append журнала и сохранение истории завершают выпуск; повтор сверяет release_id и восстанавливает незавершённое намерение без второго события.
Ошибка os.replace ДО commit и намеренный сбой ПОСЛЕ commit — разные случаи: в первом старые байты сохраняются, во втором указатель уже новый, но WAL позволяет завершить журнал при следующем запуске. Это single-writer протокол, не решение конкуренции нескольких издателей. События выпусков отделены от журнала попыток; release_id учитывает manifest (модель и runtime) и полное решение, включая evaluation_run_id.
Восемь дополнительных отрицательных опытов — evidence/negative-cases.json: отказ, неполнота, truthy string, чужой model_id, NaN, ошибка replace, изменение runtime с пересчитанным хешем и подмена raw. Везде зафиксированы accepted SHA до/после. Проверки схемы/допуска и несовместимые веса не повторяются; Prefect retries=0. Только сетевое скачивание артефактов имеет ограниченный retry для временных ошибок.

6. API и реально загруженная версия

model_id: baseline:Qwen/Qwen3-0.6B@c1899de289a04d12100db370d81485cdf75e47ca
runtime_sha256: dbfbcfef03572b8a7369c3a0a47e8f1f9e2aa9516f266dc22dc2f548e24b265a
Manifest связывает файлы весов/конфигов/токенизатора, base revision, template, system, greedy, seed 42, max_new_tokens 32, enable_thinking false, dtype bfloat16, MPS и точные версии inference-библиотек. Хеши файлов проверяются до публикации и до загрузки. API не читает params.yaml и не меняет модель от редактирования указателя.
FastAPI lifespan запускает фоновую загрузку и настоящий прогрев; health — жизнь процесса, ready — загруженные веса и завершённый прогрев. В evidence/ready-observations.json сохранены реальные health/ready статусы. Блокировка допускает только одно вычисление, обработчик HTTP остаётся доступным в event loop. Debug включён только явным флагом в локальном стенде.
Реальный ответ из evidence/real-smoke.json:
{
  "answer": "{\"answer\": \"A\"}",
  "output_tokens": 7,
  "model_id": "baseline:Qwen/Qwen3-0.6B@c1899de289a04d12100db370d81485cdf75e47ca",
  "runtime_sha256": "dbfbcfef03572b8a7369c3a0a47e8f1f9e2aa9516f266dc22dc2f548e24b265a",
  "request_id": "72511f34-cab2-47f8-9536-4e19fdac2e36",
  "queue_seconds": 1.5458004781976342e-05,
  "generation_seconds": 0.6592126250034198,
  "service_seconds": 0.66219733300386
}
Дословное совпадение со старым ответом baseline: True.
Предел входа — 2048 символов и 512 токенов с system/template. В настоящем API max_new_tokens строго равен 32; у STUB допустимы 1–32 для проверки прототипа. Изменять generation settings на запрос нельзя. Шесть неверных реальных запросов вернули 422, calls остался 2 → 2. Ответ содержит UUID request_id, loaded model_id/runtime_sha256, output_tokens и времена.
A → B → A проверено на двух STUB-версиях: до перезапуска ответа остаётся A, после загрузки B — B, затем управляемый откат к ранее принятой A и перезапуск. Реальный backend отдельно перезапущен с тем же manifest; model_id/runtime_sha256 и настоящий ответ зафиксированы в real-restart.json. Вторую настоящую принятую версию не выдумывали.

Один и тот же список восьми вопросов, по 32 разрешённых новых токена; фактически по 56 токенов за каждый пакет. Все 16 попыток, статусы/ошибки, server/client IDs, generation/queue/service/client time — evidence/requests.jsonl. Ошибок в этой выборке нет; mean/max для ошибок равны null, а не выдуманному нулю. Таблица — docs/benchmark.csv.
При двух клиентах вычисления сериализуются, запросы ждут блокировку; среднее ожидание выросло примерно до 0.87 с. Этот прогон также показал более медленные вычисления/меньший throughput. Он не доказывает универсальную деградацию от concurrency=2: ноутбук не изолирован от других локальных служб, прогрев/нагрузка меняются, выборка мала. Увеличение клиентской параллельности здесь не включает batching движка.
Prefill обрабатывает контекст и строит KV-cache; decode последовательно добавляет токены с использованием этого кеша. Его память растёт с длиной контекста, числом слоёв и активных последовательностей. Backend здесь обычный Transformers с одной блокировкой; paged KV-cache, continuous batching и prefix reuse SGLang/vLLM не измерялись. JSON приходит целиком: измерена полная задержка, не TTFT/ITL. Надёжный p95 по восьми запросам не заявляется.
