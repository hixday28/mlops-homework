# Разбор пяти дефектов

## 1. Данные попадали в Git

В `.gitignore` не было `data/`, а DVC учитывал не все выходы. Обычный `git add .` мог сохранить JSONL навсегда в истории.
Добавлен запрет на весь `data/`; raw, clean, train, val, test и атрибуция объявлены в DVC. Тематический снимок хранится через `source.dvc`, указатель находится вне игнорируемой папки.
Проверка: `git ls-files data/` возвращает **0 файлов**, `git check-ignore data/raw.jsonl` подтверждает правило; `make check`, пункт 1, сверяет все пять обязательных выходов. Данные отправлены в локальный remote через `dvc push`.

## 2. Смена версии не пересчитывала данные

У collect не было `params`, у clean — зависимости от raw; у split были объявлены не все файлы. DVC не видел важные изменения.
Добавлены зависимости от входных файлов и кода, конфигурация collect/clean/split, все три выхода сплита и метрики collect. Split зависит от результата diversity, поэтому не может обойти гейт. Contamination — отдельная стадия после split.
Проверка версии в `make check`: **1200 → 1550** сырых примеров, MD5 clean меняется **d6159094 → 6b95d4de**. После восстановления версии `dvc status` сообщает, что данные актуальны. Сравнение сохранённых версий выполняется через `make diff`.

## 3. Случайный сплит разносил одну группу по разным частям

В заготовке считались размеры групп, но использовался `row_split` по отдельным строкам. Нормализация темы сама по себе не участвовала в распределении.
Теперь один хеш группы определяет один сплит; обе версии сохраняют принадлежность уже существовавших групп. Дедупликация выполняется до разбиения.
На очищенной v1 исходный случайный алгоритм с seed=42 дал **35 общих групп train/test**, исправленный — **0**. Пересечений по ID и текстам в этой контрольной выборке и до исправления было 0: это не выдается за исправленные текстовые дубли.
Отдельный гейт проверяет train↔val, train↔test и val↔test по четырём критериям, возвращая ненулевой код при нарушении.

## 4. Near-dup был пропущен

В clean после точной дедупликации стояло `near = set()`: флаг и порог не использовались. Почти одинаковые вопросы оставались.
Добавлен поиск по нормализованным четырёхсловным шинглам. Вместо вероятностного ответа LSH используется полный инвертированный индекс и точный Жаккар: порог 0.85 означает реальное значение сходства. Та же реализация используется в contamination; несовпадение порогов отвергается конфигурацией.
В контрольных **5 примерах** из задания удаляется **1 точный и 1 почти-дубль**, остаются **3**. Все **3** подложенных контакта маскируются. Отдельный тест сравнивает индекс с полным попарным расчётом при порогах 0.5, 0.85 и 1.0.
В реальных версиях найдено **0 точных и 0 почти-дублей**. Синтетические дубли были только в тестах; в датасет ради красивых счётчиков они не добавлялись.

## 5. Diversity сообщал о нарушениях, но не останавливал пайплайн

В исходном main список нарушений приводил только к print, после чего процесс завершался успешно.
Теперь метрики с `passed=false` сохраняются, затем стадия завершает работу с ненулевым кодом и перечисляет фактические значения и пороги. Выход diversity включён в зависимости split.
Контрольный набор из **1200 строк**, **1 системного промпта** и **1 группы** отвергается. Реальная v1: **1148 строк, 4 промпта, 637 групп**, p90/p10 = **12.68** — проходит без снижения порогов. Все семь условий diversity остались исходными.

## Дополнительные проверки

- Битая третья строка останавливает clean с сообщением `raw.jsonl:3`; пустые topic и неправильные роли также запрещены.
- Маскирование выполняется до дедупликации: вопросы, различающиеся только контактами, после него совпадают.
- Источник закреплён ревизией; загрузчик проверяет SHA256 архива.
- Метрики не содержат времени исполнения, поэтому повторный запуск не создаёт случайную разницу артефактов.
- `make check`: все восемь пунктов проходят. `make test`: девять регрессионных тестов проходят.
